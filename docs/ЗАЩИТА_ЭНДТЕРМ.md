**Вопросы к Aidana:**
- *Что такое AJAX?* Асинхронный запрос из JavaScript к серверу без перезагрузки страницы. У нас он сделан через `fetch` и `async/await`.
- *Сколько асинхронных операций?* Шесть:
  1. каталог;
  2. проверка группы;
  3. проверка email при регистрации;
  4. отзыв;
  5. прогресс урока;
  6. смена статуса в админке.
- *Как обрабатываются ошибки fetch?* В `apiRequest()`. Если нет сети, выбрасывается `Network error`. Если сервер ответил не JSON — «invalid answer». Если HTTP 401/403/409/422/500 — берётся текст ошибки из JSON. Вызывающий код ловит ошибку в `catch` и показывает toast или сообщение.
- *Зачем `lastRequest` в courses.js?* При быстром наборе старый медленный ответ может прийти позже нового. Мы его игнорируем.
- *Почему URL меняется?* `history.replaceState`: результат поиска можно обновить или отправить ссылкой.

## 2. Nazerke: формы, валидация, безопасность

**Показывает регистрацию:**
1. Нажимает Register на пустой форме → 5 ошибок.
2. Вводит `student@educonnect.kz` → во время ввода появляется подсказка «already registered» (AJAX).
3. Вводит пароль `abc1234` → «at least 8 characters».
4. Вводит разные пароли → «Passwords do not match».
> «Сначала форму проверяет JavaScript (`auth.js`), но его можно отключить. Поэтому PHP проверяет всё ещё раз в `validate_registration()` в `includes/validation.php`: формат, длину, уникальность email в базе.»

**Открывает `register.php`:**
> «Пароль сохраняется не текстом, а хэшем: `password_hash()`, это bcrypt. При входе `password_verify()` сравнивает введённый пароль с хэшем. Все запросы к базе подготовленные: `prepare` и `execute` с `?`. Данные отправляются отдельно от SQL, поэтому SQL-инъекция невозможна.»

**Показывает вход:**
- неверный пароль → «Incorrect password»;
- неизвестный email → «No account found»;
- после 5 ошибок форма блокируется на 60 секунд.

**Безопасность (показать в коде `includes/functions.php` и `includes/auth.php`):**
- **XSS:** всё выводится через `h()` = `htmlspecialchars`. В контактной форме написать `<script>alert(1)</script>` → в админке это просто текст.
- **CSRF:** в каждой форме скрытый токен `csrf_field()`, сервер сверяет его через `hash_equals`. Без токена → 403.
- **Сессии:**
  - `session_regenerate_id(true)` после входа;
  - cookie с `httponly` и `SameSite`;
  - Logout — это POST-форма, сессия уничтожается.
- **Cookie:** галочка «Remember my email» сохраняет только email на 30 дней.
- **Права:** студент открывает `/admin/` → 403. Открывает чужую `confirmation.php?id=…` → 403. Отменить чужую запись нельзя: в запросе `WHERE id = ? AND user_id = ?`.

**Вопросы к Nazerke:**
- *Зачем валидация и в JS, и в PHP?* JS — для удобства пользователя (мгновенно). PHP — для безопасности: JS можно отключить или отправить запрос в обход формы.
- *Почему не хранить пароль как есть?* Если базу украдут, пароли не узнают. Хэш односторонний, и у каждого пароля своя «соль».
- *Что такое CSRF?* Чужой сайт заставляет браузер пользователя отправить запрос на наш сайт. Токен этот сайт знать не может.
- *Что такое session fixation?* Злоумышленник заранее подсовывает свой id сессии. Мы меняем id при входе.
- *Как проверяется фото?* Размер до 1 MB и настоящий MIME-тип через `finfo` (не расширение файла). Имя файла случайное. В `uploads/.htaccess` запрещено запускать PHP.

## 4. Kirill: база данных, админка, SQL

**Открывает phpMyAdmin → educonnect → Designer** (или `docs/SQL_QUERIES.md`):
> «13 таблиц: users, categories, teachers, courses, course_features, course_groups, group_sessions, enrollments, lessons, materials, lesson_progress, reviews, contact_messages. Есть первичные и внешние ключи, `UNIQUE` (email, один отзыв на курс) и `CHECK` (рейтинг 1–5, конец урока позже начала).»

**Главное замечание апайки — открывает `includes/enrollment.php`, `find_schedule_conflicts()`:**
> «Группа — это дни и время занятий, они лежат в `group_sessions`. Запрос соединяет новую группу с группами, где студент уже учится. Конфликт есть, если совпадает день недели, время пересекается (`start1 < end2 AND start2 < end1`) и даты групп тоже пересекаются. Поэтому 14:00 и 14:00 — конфликт, и 14:00–15:30 с 14:30–16:00 — тоже.»

**`enroll_user()` — транзакция:**
> «`beginTransaction`. Затем `SELECT … FOR UPDATE` блокирует строку группы, чтобы двое не заняли последнее место одновременно. Дальше проверки: группа не закончилась, студент не записан на этот курс, нет конфликта, есть место. Затем `INSERT` и `commit`. Если что-то не так — `rollBack`, ничего не сохраняется.»

**Админка** (Logout → `admin@educonnect.kz` / `admin123`):
- **Dashboard:** статистика, выручка за месяц, группы, которые скоро стартуют.
- **Enrollments:** меняет статус Pending → Confirmed. Это AJAX, счётчики обновляются без перезагрузки.
- **Courses:** `+ Add course` → пустая форма показывает ошибки → заполняет → переходит к группам (в группе время конца раньше начала → ошибка) → Lessons → добавляет материал.
  - Delete «Introduction to Python» → «cannot be deleted»: внешний ключ `RESTRICT`, ошибку БД мы ловим и показываем понятно.
  - Delete нового курса → удаляется вместе с группами и уроками (`CASCADE`).
- **Reports:** 9 SQL-отчётов: JOIN, LEFT JOIN, подзапросы, COUNT/SUM/AVG/MAX, GROUP BY + HAVING, отчёт по месяцам. Кнопка «Show SQL» показывает запрос.
- **Tests:** 24 автотеста. Тесты валидации, границ, бизнес-логики, прав доступа и ограничений БД проходят все.

**Вопросы к Kirill:**
- *JOIN и LEFT JOIN — разница?* JOIN оставляет только строки, у которых есть пара. LEFT JOIN оставляет все строки левой таблицы, даже без пары (отчёт «студенты без записей»: `WHERE e.id IS NULL`).
- *WHERE и HAVING?* WHERE фильтрует строки до группировки, HAVING — группы после `GROUP BY` (например, «выручка > 0»).
- *Зачем транзакция?* Несколько действий выполняются как одно: либо всё, либо ничего. И блокировка не даёт двоим взять последнее место.
- *Что будет при удалении пользователя?* `ON DELETE CASCADE` удалит его записи, прогресс и отзывы. Сообщения останутся (`SET NULL`).
- *Как защищён ORDER BY в каталоге?* Сортировку нельзя передать через `?`, поэтому значение выбирается только из белого списка `SORT_OPTIONS`.
